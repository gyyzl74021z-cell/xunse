# 项目与提交规范 v1.0

适用阶段：第一周准备，以及后续开发。规范负责人为 E；任务内容负责人按 README 分工执行。

## 1. 工作流

main 保存团队检查过的成果。日常工作先从更新后的 main 新建个人任务分支，提交并推送，再创建 PR；由另一位组员检查、合并后同步 main。课程小组可以先用此约定协作，无需先配置复杂分支规则。

分支示例：`docs/requirements-alice`、`data/chart-bob`、`chore/environment-chen`。使用英文小写、数字、斜线与短横线。一个分支聚焦一个任务。

## 2. 提交信息

格式：`类型: 清楚描述本次修改`。

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| docs | 文档与台账 | docs: 补充环境安装步骤 |
| data | 数据清单、标注与来源说明 | data: 登记图表素材来源 |
| chore | 目录、依赖和项目配置 | chore: 固定图像处理依赖版本 |
| feat | 后续新增功能 | feat: 添加颜色名称显示 |
| fix | 后续问题修复 | fix: 修正图片方向处理 |
| test | 后续验证记录 | test: 记录颜色识别测试结果 |

第一周主要使用 docs、data、chore。每次提交只包含相关变更，避免“更新”“最终版2”等不清楚的描述。

## 3. PR 检查

PR 描述写清：对应任务、修改内容、核对方法、尚未完成的事项。审阅人检查路径是否正确、文字是否完整、状态与证据是否对应，以及是否把本地环境和构建产物误提交。

不随意删除他人成果，不强制推送覆盖主分支。发生冲突时由相关修改者一起确认应保留的内容。

## 4. 文件与目录

- 文档用 UTF-8 编码，Markdown 统一使用 .md。
- Python 后续使用 snake_case 文件名与函数名、4 空格缩进；Android 遵循统一工程所选语言的常规命名。
- 文档以清楚的稳定文件名保存，版本信息写在文内，历史由 Git 管理。
- 数据放 dataset，模型相关内容放 model，Android 工程放 app-android，PC 演示放 demo-pc，文档放 doc，测试证据放 test-report。
- Git 不保存空目录。当前目录中已放 README.md，上传时保留这些说明文件。

## 5. 数据与大文件

素材来源、用途和使用条件在 dataset/SOURCES.md 登记。C、D 负责人各自负责数据质量，E 负责目录和交付路径一致。

允许公开且体量合适的图片可放仓库；大量原始素材、训练权重和视频通过团队约定的存储方式共享，在 README 登记位置、版本和校验信息。GitHub 普通 Git 存储阻止大于 100 MiB 的单文件；网页上传单文件最多 25 MiB。需要时采用 Git LFS 或外部资料存储，不把虚拟环境与安装包上传仓库。

公开仓库不提交账号口令、令牌、Android 签名密钥等本地凭据。提交之前在 Changes 中检查文件列表。

## 6. 环境变更

主要版本按 ENVIRONMENT.md 安装；基准机导出完整锁文件后统一使用。升级先在个人环境验证，再提出 PR，同步手册、锁文件和团队登记表；不得由某人直接升级全队基线。

## 7. 进度与验收

每名负责人更新自己任务的状态和成果路径，E 每周汇总。状态只使用：未开始、进行中、待验收、已完成、受阻。已完成必须有成果位置与验收人；有文件草稿但未审核时填待验收。
